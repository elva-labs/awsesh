# Feasibility: AWS profile selection with nono

**Decision: GO for a constrained prototype; NO-GO for release against arbitrary host AWS profiles.** nono can sign as either of two approved identities at the same endpoint in one sandbox session. Its route allowlist controls which named providers can be selected; it does not constrain what those host profiles can resolve. The current `awsesh` [shell export](../../packages/awsesh/src/util/styled-output.ts#L49-L60) hands out real session credentials and is unsuitable as the sandbox launch environment.

## Pinned evidence

Reviewed [nono v0.82.0](https://github.com/nolabs-ai/nono/releases/tag/v0.82.0), commit `f1e0a7ac2cf44709a2982c07b5ca1273e0d5a9ba`, which includes [PR #2277](https://github.com/nolabs-ai/nono/pull/2277). The [versioned docs](https://github.com/nolabs-ai/nono/blob/f1e0a7ac2cf44709a2982c07b5ca1273e0d5a9ba/docs/cli/features/credential-injection.mdx#L806-L858) describe one `aws_auth.profiles` map per endpoint. A sandbox client selects a placeholder profile via `--profile` or `AWS_PROFILE`. For each HTTP/1.1 request inside an intercepted HTTPS tunnel, the proxy [selects the provider by the placeholder key ID](https://github.com/nolabs-ai/nono/blob/f1e0a7ac2cf44709a2982c07b5ca1273e0d5a9ba/crates/nono-proxy/src/aws/route.rs#L110-L145), [removes the client auth headers](https://github.com/nolabs-ai/nono/blob/f1e0a7ac2cf44709a2982c07b5ca1273e0d5a9ba/crates/nono-proxy/src/tls_intercept/handle.rs#L1801-L1838), and signs with the selected host provider. Placeholders are selectors; every process with access to the route can select any identity on it. All mapped identities share the route's endpoint policy.

| Acceptance criterion | Result | Evidence |
| --- | --- | --- |
| Two explicit identities can target the same service, region, and endpoint in one session | Observed on macOS arm64 | Two simultaneous stock CLI requests reached the same loopback TLS endpoint with distinct expected host access IDs in one standalone proxy run and again in one supervised sandbox run. Two overlapping credential routes [are ambiguous](https://github.com/nolabs-ai/nono/blob/f1e0a7ac2cf44709a2982c07b5ca1273e0d5a9ba/crates/nono-proxy/src/tls_intercept/handle.rs#L719-L749). |
| Missing, unparseable, repeated, or unmapped selector cannot choose a fallback | Missing and unmapped observed; other cases source-reviewed | Unsigned and unmapped requests returned `403` and never reached the loopback upstream. The handler also rejects a selector it cannot parse or one sent in multiple Authorization headers. Every mapped profile must exist before the signing route is installed; the binary reported an unavailable route with empty host config. |
| No default identity or arbitrary host credential access | Observed for the scoped setup; requires integration controls | Neither a configured synthetic `default` identity nor synthetic supervisor environment keys were selected. The child could not read either of two synthetic credential files. Map entries use [named profile-file providers](https://github.com/nolabs-ai/nono/blob/f1e0a7ac2cf44709a2982c07b5ca1273e0d5a9ba/crates/nono-proxy/src/aws/route.rs#L302-L408) without implicit credential-chain fallback, but the validator accepts an explicit `default` target and accepts `aws_auth: {}`, which uses the default chain. Named profiles can themselves use `source_profile`, `credential_source`, or `credential_process`; a name allowlist alone cannot bound those sources. |
| Ordinary client profile selection through the proxy | Observed with AWS CLI 2.34.12 | Both `aws --profile` and `AWS_PROFILE` worked with a regular placeholder-only config and the session CA. Presigned URLs are out of scope; the pinned [HTTP/2 intercept](https://github.com/nolabs-ai/nono/blob/f1e0a7ac2cf44709a2982c07b5ca1273e0d5a9ba/crates/nono-proxy/src/tls_intercept/handle.rs#L954-L958) and [reverse-proxy](https://github.com/nolabs-ai/nono/blob/f1e0a7ac2cf44709a2982c07b5ca1273e0d5a9ba/crates/nono-proxy/src/reverse.rs#L315-L321) paths do not implement AWS signing. Other clients were not tested. |

For a prototype, generate the route only from an explicit host-approved allowlist and reject `default`, implicit-chain routes, and unapproved credential sources or transitive profile dependencies. Use supervisor-controlled host configuration; keep it, its caches, and any other credential paths outside sandbox access. Give the child only the placeholder config and required proxy settings, with no inherited AWS credential or profile selection variables and no direct AWS egress. Before release, verify the intended CLI/SDK clients and supported OSes through a real sandbox, including concurrent distinct identities on one endpoint, denial without a selection, and isolation from host credentials.

## Local verification

- On macOS arm64, extracted the official release into a temporary directory. Its SHA-256 matched the digest in GitHub release metadata (`a11760b1d5e947152d1fdc6497b2aba2e4185061a56390b2f1137c83cef3b5a4`); `nono --version` printed `nono 0.82.0`.
- With a clean environment and isolated home, piped JSON to `nono profile validate --strict /dev/stdin`. Exit `0`: two mappings, a one-entry map, a map targeting `default`, and `aws_auth: {}`. Exit `1`: `profile` plus `profiles`, an empty map, an invalid placeholder key, and duplicate target profiles. `nono profile groups deny_credentials` reported the group required and showed `~/.aws` in its deny list.
- With both host AWS files set to `/dev/null` and metadata disabled, standalone proxy startup reported the mapped profile missing and the route unavailable; the listener started and exited `0` on SIGINT.
- Started one authenticated `nono proxy` on an ephemeral loopback port with one `aws_auth.profiles` route to `https://localhost:<port>`. Used separate regular files for synthetic supervisor credentials and client placeholders, and ephemeral TLS CAs without changing system trust. Two AWS CLI `sts get-caller-identity --endpoint-url` requests selected `dev-ro` via `--profile` and `staging-ro` via `AWS_PROFILE`. The upstream held each response until both requests arrived, recorded only the signing access IDs, and returned each ID to its caller. Both calls exited `0` with their expected IDs: `EXAMPLELOOPBACKDEV01` and `EXAMPLELOOPBACKSTG01`. With the same proxy still running, an unmapped placeholder and an unsigned `--no-sign-request` call each returned `403` (CLI exit `255`); the upstream count remained exactly two.
- Repeated the two concurrent calls inside one supervised `nono run`. The sandbox inherited no AWS credential or profile selectors, could read its regular placeholder config, and was denied reads of the supervisor's synthetic `~/.aws/credentials` and a separate synthetic credential file. Both requests reached upstream with the two expected signing IDs and the sandbox exited `0`. The built-in macOS system filesystem groups initially overlapped the protected state directory under `/private/var`; the successful run used narrower read grants.
- No live AWS traffic or real credentials were used. The upstream recorded access IDs without validating signature bytes. Upstream tests were read, not run. Coverage is limited to macOS arm64, AWS CLI 2.34.12, HTTP/1.1, and synthetic file-backed host profiles; SSO, role chains, other clients, and other platforms remain unverified.
